1. PROJECT OVERVIEW
==================================================

- Project Name: uber-backend-mvp (Uber-Style Ride-Hailing Backend MVP)
- Backend Location: c:\Uber\backend
- Current Architecture:
  The backend follows a decoupled dual-pipeline architecture:
  1. High-frequency Real-Time Location Pipeline: Driver GPS updates (emitted every 1-3 seconds) are ingested exclusively via WebSockets (Socket.IO), converted to Uber H3 resolution 8 hex cell indices, and indexed in Redis sets and hashes. High-frequency location updates are isolated from the relational database.
  2. Low-frequency Relational Data & Lifecycle Pipeline: User authentication, driver profiles, ride lifecycle management, and final fare audits are handled over Express REST endpoints and persisted in PostgreSQL using Prisma ORM.
  3. Embedded 7-Driver Simulator: Generates 7 simulated drivers (D2..D8) that feed into the exact same location update pipeline as the real driver (D1).
- Current Tech Stack:
  - Runtime: Node.js 25.6.0
  - Language: TypeScript 5.7.3 (Target: ES2022, Module: NodeNext)
  - HTTP Framework: Express 4.21.2
  - Real-Time Protocol: Socket.IO 4.8.1
  - Database: PostgreSQL 16 + PostGIS (Docker image: postgis/postgis:16-3.4)
  - ORM: Prisma 5.22.0
  - In-Memory / Live Cache: Redis 7 (ioredis 5.4.2) with custom MemoryRedis fallback store
  - Geospatial Indexing: Uber H3 (h3-js 4.2.0, resolution 8)
  - Validation: Zod 3.24.2
  - Security / Auth: JSON Web Tokens (jsonwebtoken 9.0.2), bcryptjs 2.4.3
  - Testing: Jest 29.7.0, Supertest 7.0.0, ts-jest 29.2.5
- What the Backend is Intended to Do:
  - Serve a college demonstration project (target deadline: Oct 10) supporting 1 real rider, 1 real driver (phone GPS), and 7 simulated drivers.
  - Ingest real-time driver coordinates and maintain live spatial indexes.
  - Find and rank the Top 8 nearest available candidate drivers for a ride request using H3 k-ring disk search and Haversine distance.
  - Enforce ride lifecycle states (REQUESTED -> DRIVER_ASSIGNED -> DRIVER_ARRIVING -> DRIVER_ARRIVED -> IN_PROGRESS -> COMPLETED / CANCELLED).
  - Calculate upfront and completed fares based on distance, time, and base minimums.

  Calls locationService.updateDriverLocation({ driverId, latitude, longitude, heading, speed, timestamp }, DriverStatus.ONLINE).
- Whether Simulator Uses Same Backend Pipeline as Real Drivers:
  YES. The simulator directly invokes locationService.updateDriverLocation, executing the identical H3 cell conversion, Redis set migration, and live location hashing as real drivers sending WebSocket pings.

9. MATCHING ENGINE
==================================================

Execution Flow:

Rider GPS
 ↓
H3: IMPLEMENTED
  - Rider pickup coordinates (pickupLat, pickupLng) converted to H3 resolution 8 index via h3Service.latLngToCell().
 ↓
Candidate drivers: IMPLEMENTED
  - Expanding k-ring loop: starts at radius k=0 (center hex) and expands up to k=4 (covering ~2.5km radius).
  - For each hex cell in the ring, queries Redis Set `h3:<cell>:drivers` to collect candidate driver IDs until at least 8 drivers are found or max ring is reached.
 ↓
Filtering: IMPLEMENTED
  - For each collected driver ID, retrieves live location hash from Redis.
  - Verifies driver location exists and status is DriverStatus.ONLINE.
 ↓
Distance/ETA: IMPLEMENTED
  - Calculates straight-line geodesic distance in km using Haversine formula (calculateHaversineDistance).
  - Calculates estimated travel time in minutes assuming 30 km/h average urban speed (estimateTravelTimeMinutes).
  - Fetches driver and vehicle record from Prisma with a 300ms timeout fallback.
 ↓
Ranking: IMPLEMENTED
  - Candidate driver list is sorted in ascending order of distanceKm: candidateDetails.sort((a, b) => a.distanceKm - b.distanceKm).
 ↓
Top 8: IMPLEMENTED
  - Slices sorted array to maximum 8 drivers: candidateDetails.slice(0, maxDrivers).

Algorithm Summary:
The matching algorithm uses Multi-Ring H3 Spatial Clustering with Haversine Proximity Ordering:
1. Spatial indexing filters available drivers by geographic proximity without full-table scans.
2. Iterative disk expansion minimizes search radius to only as many rings as needed to find 8 candidates.
3. Fine-grained ranking uses true great-circle distance rather than hex distance to ensure optimal ordering.
